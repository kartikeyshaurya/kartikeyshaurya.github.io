Projects Freight & Logistics AI

A chat agent that reads the TMS and asks before it writes

A supervisor model and seven specialist agents answer freight brokers' questions from live TMS data and prepare changes that run only after the broker approves the exact action.

By Kartikey Shaurya · Valora Broker Agent · Creed Infotech, for ValueLoads

The problem

Freight brokers on the ValueLoads TMS portal work across many screens: shipments, shippers, carriers, the load board, aging, claims and reports. The shipment is the hub that ties them together, so a simple question like "which of my loads deliver today, and is that shipper over their credit limit?" means clicking through several pages and stitching the answer together by hand.

The API behind the portal is large and inconsistent, and the data is real: real freight, real money, and free text written by outsiders. Any assistant had to answer from live data, never do more than the broker is allowed to do, and never change a record without a person deciding.

How I thought about it

I did not start with prompts. I started by mapping the API: a generated reference, a live probe of every read route a broker can reach, and one document per portal page that maps each column to the response field it comes from. That evidence showed me the API could not be trusted by its spec. Some read requests changed state, some routes failed, and identifiers came in more than one form. It also meant every tool I wrote could point back to something I had observed.

That finding shaped the safety model. I could not classify a tool as safe because of its HTTP verb, so I set each tool's effect by hand: read, read with an outside service, write, or write that is hard to undo. And I split every write into two halves. The model can only prepare a write, which validates it and builds a preview. Committing it is plain code that runs after the broker approves the exact payload on a confirmation card. Writes are also switched off globally by default.

For identity, I chose to have the agent act with the broker's own TMS session instead of a service account. The TMS already enforces permissions and logs the real user, so the agent can never do more than the person using it, and I did not have to rebuild an authorisation layer. The session is never stored on our side.

For structure, one agent with every tool kept choosing the wrong one and filling its context with wide records. I moved to a supervisor that delegates to seven specialists (shippers, carriers, capacity, shipments, finance, insights and container quotes). Each specialist starts with a fresh context and sees only its own small set of tools, and specialists cannot call each other, so every cross-domain step goes back through one place I can debug. My design document proposed LangGraph, but once the approval pause turned out to be a durable database row plus a new turn, a hand-written loop was simpler to stream, budget, trace and test.

What I built

  • A supervisor and seven specialist agents on the OpenAI Responses API with strict function tools, plus fast-path tools for the most common questions.
  • A single tool gateway that every call passes through: allowlist, permission check, response shaping, redaction of sensitive fields, caching and audit.
  • A prepare-then-commit write flow with approve, edit and reject on a confirmation card, idempotent approvals, expiry, and a stronger warning for actions that cannot be undone.
  • A streaming chat UI in React that shows live steps, structured result cards and suggested next actions.
  • Attachment handling for PDFs, images and office documents: text extraction, document-type classification, scrubbing of identity numbers, and approved upload to the TMS.
  • Exact conversation replay, so each thread resumes with the same model-facing history and prompt caches stay warm.
  • An admin panel with per-user agent access, monthly spend caps, a workspace budget, usage analytics and a tool-call audit log.
  • Prompt-injection defences treating all outside text as data, backed by an adversarial test sheet that is part of the release gate.

What happens when a broker asks the agent to change something

  1. The broker types a request, for example to cancel a shipment because the shipper asked.
  2. The supervisor delegates a one-sentence task to the shipment specialist.
  3. The specialist reads the shipment through the gateway, and the result streams to the UI as a card.
  4. The specialist calls the cancel tool, which only prepares the action: it checks the broker's permission, validates the input and builds a preview. Nothing is sent to the TMS.
  5. The specialist stops at once, and the broker sees a confirmation card showing exactly what will be sent and who it affects.
  6. When the broker approves, code (not the model) commits the action with the broker's current session, records it in the audit log and clears stale cached reads.
  7. If the TMS times out after the request was sent, the action is marked unknown and the broker is told to check the record, instead of the system guessing and risking a duplicate.

Decisions and trade-offs

The agent acts with the broker's own TMS session, never a service account.

Why
The TMS already enforces permissions and logs the real user, so the agent can never do more than the broker.
Instead of
A service account with our own permission layer on top.
The cost
When the session expires the broker has to reconnect, and scheduled work with no user present is not possible yet.

The model prepares writes; code commits them after a human approves.

Why
The broker approves the exact payload that will be sent, and the commit path is separate code that re-checks access.
Instead of
Letting the model call write endpoints directly behind an "are you sure?" prompt.
The cost
One extra click per write, more code per write tool, and only one pending write per conversation.

Each tool's effect is set by hand, not inferred from the HTTP verb.

Why
The API probe found read requests that send invites or change state, and outside lookups that may cost money.
Instead of
Treating reads as safe and everything else as a write.
The cost
Every new tool needs a human decision, which is the point.

Specialists with fresh contexts and narrow tool sets.

Why
A small tool list keeps prompts short and tool choice accurate, and calls outside a specialist's set are rejected even if the model tries.
Instead of
One agent with every tool, or specialists that can call each other.
The cost
Extra model calls and latency per delegation, capped by per-turn budgets.

A hand-written supervisor loop instead of LangGraph.

Why
The approval pause is just a durable row and a new turn, and a plain async loop made streaming, budgets and tracing easier to control and test.
Instead of
A LangGraph graph with checkpoints and interrupts, as my own design proposed.
The cost
I own the loop code and give up built-in graph visualisation, but kept the seams that would make a later move possible.

Stable system prompts and a fixed tool list per role.

Why
Keeping the date, user and current page out of the system prompt and sorting tools keeps the provider's prompt cache warm, which cuts cost and latency.
Instead of
Personalised prompts and per-user tool lists.
The cost
A tool the broker cannot use shows up as a "forbidden" result rather than being hidden.

The hard parts

  • An API I could not trust by its spec

    Read requests with side effects, failing routes, misnamed paths and mixed identifier types meant the documentation alone was not enough. I built evidence first: a live probe and a page-by-page field map with every claim marked as observed or inferred. Each tool records what it relies on, and the model is taught that an empty result is not an error.

  • Prompt injection through business data

    Shipper notes, claim comments and uploaded PDFs are written by outsiders. I treated them as data at every layer: clearly framed blocks, a shared "data is not instructions" rule in every prompt, no raw endpoints, strict per-specialist tools and human approval for writes. Then I wrote adversarial tests for each path.

  • Replaying multi-agent conversations exactly

    The model provider keeps no conversation state for us, and reasoning models need their earlier reasoning echoed back. I store the exact model-facing items for every message, so each turn replays byte for byte, prompt caches stay valid, and older threads still render if the provider changes.

  • A fragile upstream under load

    The test environment started failing when it received several requests at once. I put concurrency limits in the one client that talks to the TMS, retried only idempotent reads, and mapped TMS status codes to a small set of outcomes that both the model and the UI understand.

What I'd do next

  • Turn writes on in a disposable environment and exercise every commit path end to end.
  • Build an evaluation harness per specialist for routing, tool choice and grounding, and run it in CI.
  • Move document extraction to a background worker so large scans do not hold a request open.
  • Add server-side session refresh so scheduled turns, such as a morning brief, become possible.

What I took away

An agent is only as safe as the narrowest path it has to the real system. Putting every call through one gateway, acting as the real user, and separating "prepare" from "commit" meant I could reason about safety in one place instead of in every prompt. The research I did before writing code, mapping what the API actually does rather than what its spec says, was the part that made the rest of the design possible.
