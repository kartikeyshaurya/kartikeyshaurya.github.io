A document chatbot that would rather say it doesn't know

Built with a colleague: a document Q&A service that combines keyword and semantic search, checks what it retrieves before answering, and ships as a metered API with an admin portal.

By Kartikey Shaurya · Hybrid Search RAG · Built with a colleague

The problem

Teams have internal documents (PDFs, Markdown, text files) and want a chatbot that answers from them without making things up. Two failures come up again and again. Dense vector search misses exact terms like product codes, acronyms and error strings. And a model handed loosely related passages will answer confidently anyway.

The users were integrators calling the service from their own apps and backends, and admins who upload documents, issue keys and watch usage. For both groups the API was the product. The chat page we shipped is a test console, not the end-user interface.

How I thought about it

We started from the two failure modes and treated them as separate problems. For retrieval misses, we ran keyword and semantic search together: dense embeddings for paraphrase, BM25 sparse vectors for exact tokens. The real question was how to merge them. A weighted sum of scores needs normalisation and a tuned weight per corpus, because cosine similarity and BM25 scores live on different scales. Reciprocal Rank Fusion combines the lists by rank instead, so it needs no tuning. Qdrant can store both vectors on the same point and fuse them on the server, which gave us hybrid search in one query and one datastore instead of running a separate search engine.

For confident wrong answers, we found that the root cause was structural: top-k retrieval always returns something, even for an off-topic question. So we changed the shape of the pipeline instead of tweaking the prompt. A LangGraph state machine retrieves, has the LLM grade every chunk for relevance in one batched, structured call, and then branches. If anything relevant survives, it answers from that context only and cites its sources. If nothing survives, it returns a fixed "I don't have this information" reply.

The principle we settled on was that the decision to answer belongs to the graph, not the model, and the model only works from evidence that passed a check. Around that we built the product side: hashed, rate-limited and quota-metered API keys for integrators, and an admin portal for documents, keys and usage. One shared answer function serves the API, the command line and ingestion, so those paths can't drift apart.

What I built

  • Hybrid retrieval in Qdrant: dense OpenAI embeddings and local BM25 sparse vectors on the same point, fused with Reciprocal Rank Fusion in a single query.
  • A LangGraph workflow that retrieves, grades, and then either answers with citations or falls back to a fixed reply.
  • Batched relevance grading with a typed yes or no per chunk, so grading several chunks costs roughly one round trip instead of one per chunk.
  • An ingestion pipeline for PDF, Markdown and text that chunks with overlap, embeds each chunk both ways and keeps source and page details for citations.
  • Metered API keys that are stored only as hashes and shown once, with rotation, revocation, per-minute rate limits and monthly quotas.
  • A React admin portal for consumers, keys, document upload and deletion, and usage analytics charts.
  • Document deletion that also removes the document's vectors, so a withdrawn file stops answering questions.
  • A single-container deployment where only the API is exposed and the datastores stay on an internal network.

What happens to a question

  1. An integrator sends a question with an API key. The service hashes the key, looks it up and checks that the key and its owner are active.
  2. The per-minute rate limit and the monthly quota are checked. Over either limit, the caller gets a clear rejection with a hint about when to retry.
  3. The question is embedded, and Qdrant runs dense and BM25 search together and returns the top fused chunks.
  4. The LLM grades every retrieved chunk for relevance in one batched call, and unrelated chunks are dropped.
  5. If any chunks survive, the model answers from that context only and cites the source files and pages.
  6. If none survive, the graph returns a fixed "I don't have this information" reply instead of letting the model improvise.
  7. The request is logged for usage analytics without adding to response time, and failed requests are logged as well.

Decisions and trade-offs

Hybrid retrieval fused with Reciprocal Rank Fusion inside Qdrant

Why
Dense vectors handle paraphrase and BM25 handles exact tokens. Fusing by rank avoids calibrating two incompatible score scales, and doing it on the server means one round trip and one datastore.
Instead of
Dense-only search, or a separate keyword search engine plus a vector database with fusion in the application.
The cost
We accept a fixed fusion with no tuned weighting. Two stores would allow tuning but double the operational work.

A relevance-grading step before generation

Why
Top-k retrieval always returns something. Grading lets the graph route to a deterministic fallback instead of letting the model improvise from weak context. The grader is deliberately lenient: it drops clearly unrelated chunks rather than reranking.
Instead of
A similarity-score cut-off, or a cross-encoder reranker.
The cost
It adds one extra LLM round per question, which we kept small by grading all chunks concurrently. A cross-encoder would be cheaper per call but is another model to host.

A LangGraph state machine instead of a linear chain

Why
The pipeline has a real branch, and an explicit graph with typed state makes it easy to add nodes later, such as query rewriting or a retry when nothing relevant comes back.
Instead of
A plain chain with an if statement.
The cost
It is a little more machinery than four steps strictly need, in exchange for cheap extension later.

One shared answer function for every entry point

Why
The API, the command line and the ingestion routes all call the same function, so their behaviour can't drift apart.
Instead of
A separate code path per interface.
The cost
That one module becomes critical, so changes to it need care.

A fast hash for API keys and a slow one for passwords

Why
Keys are long random values, so a fast hash is safe and allows a direct indexed lookup on every request. Human passwords are low-entropy and need a deliberately slow hash.
Instead of
The same slow password hash for keys too.
The cost
A slow hash on every chat request would add CPU time per call and rule out indexed lookups, so the split is worth the extra rule to remember.

The hard parts

  • Staying grounded when retrieval always returns results

    Top-k search never comes back empty, so the model always had something to riff on. The fix was structural: an explicit grading step and a branch to a fixed fallback, combined with a generation prompt that says to use only the given context and cite it.

  • Grading latency growing with the number of chunks

    Grading chunks one at a time meant one LLM call after another. We switched to a single batched call with structured output, which runs the grades concurrently and returns a typed yes or no, so there is no free text to parse.

  • Usage rows missing when requests failed

    Errors weren't showing up in analytics, because the web framework drops background tasks when a handler raises. Failed requests now log inline before the error is returned, and the logger swallows its own errors so it can never break a chat request.

  • Making document deletion actually forget

    Deleting a file left its chunks in the vector store, still answering questions. Deletion now also removes every vector tagged with that document's source, which works because ingestion normalises the source name consistently.

What I'd do next

  • Conversation memory, with a query-rewrite step that turns follow-up questions into standalone ones.
  • A corrective retry loop that rewrites the query once and retrieves again before falling back.
  • An evaluation set with known source passages, to measure recall and faithfulness for dense, sparse and hybrid search and to tune chunk size and top-k from data.
  • Idempotent background ingestion and separate corpora per tenant.

What I took away

When a model misbehaves, look for the structural cause before reaching for the prompt. Retrieval that always returns something will always give the model something to improvise from, and the fix was a branch in the graph, not better wording. I'd carry that into the next system: put the decision to answer in code, and let the model work only on evidence that passed a check.
