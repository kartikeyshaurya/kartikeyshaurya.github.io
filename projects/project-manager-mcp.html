A project tracker your AI assistant can work inside, safely

An AI-native project manager that puts planning, bugs, tickets, team chat and executive reporting in one multi-tenant app. ChatGPT and Claude can create and update work through MCP, acting with the user's own permissions.

By Kartikey Shaurya · AI-native project manager · Solo build

The problem

Product teams split their work across a tracker, a chat tool, a bug form and a slide deck for leadership. Each tool has its own idea of who can see what, and the weekly summary for the CEO gets assembled by hand from all of them.

AI assistants added a new version of the same problem. People already ask ChatGPT or Claude to turn a conversation into tasks, then copy the answer across by hand. Letting an assistant write straight into a workspace is only useful if it respects the same permissions as the person, cannot invent numbers in a report, and cannot quietly burn through the AI budget.

How I thought about it

I started from the write path. Tasks get created by the UI, CSV import, ticket triage, automations, the AI assistant and MCP, and every one of those needs the same side effects: field history, activity log, notifications, watchers, webhooks, search re-indexing and a real-time broadcast. If each entry point did its own writes, each would forget something. So I wrote a short design document that makes one task service the only writer, and hung workflow rules, custom fields and dependency checks off its extension points. That is also why the app is a modular monolith: a task write touching ten concerns is one transaction there, and a saga anywhere else.

For tenancy I held one rule: the workspace is always derived on the server from the user's membership, never taken from the request. Permissions are a cumulative matrix of module and action (admin includes edit, edit includes view). The stricter layers, private projects and team scoping, sit behind flags with an access report you can review before switching them on.

For AI, the principle was facts first. Rules compute the counts, keys and dates, and the model only phrases them. Before a summary is accepted, every number in it is checked against the facts and every task reference against real tasks, and anything unsupported falls back to a plain sentence that is correct. When the AI proposes changes, it produces drafts that are checked against real projects and people, and a person approves them through the same single write path. Every model call goes through one gateway with feature flags, separate budgets for interactive and background work, and an audit record.

MCP came last and reused all of that. I built a small OAuth server on top of the existing accounts, so ChatGPT and Claude connect with the user's own login and act with the user's own permissions. The MCP server is a thin layer over the public API: it returns minimal results, labels which tools read, write or destroy, and stays read-only unless writes are deliberately switched on.

What I built

  • Planning: projects, issue keys, subtasks, epics, sprints, drag-and-drop boards with stable ordering, a backlog, a calendar and a dependency timeline
  • Task dependencies with cycle detection that is safe under concurrent edits, a per-project warn or block mode, and automatic date scheduling
  • Per-project workflows with transition rules, validated custom fields, and team-scoped projects behind a feature flag
  • Collaboration: rich-text descriptions, mentions, watchers, notifications, team chat with presence, and real-time updates over WebSockets
  • An AI gateway with feature flags, token budgets, scrubbing of secrets and personal data before any model call, prompt versions locked by tests, and an audit record per call
  • AI features on top of it: task drafting from chat and screenshots, triage, hybrid semantic search, duplicate detection, standups, digests and executive briefs
  • Scheduled executive summaries rendered to HTML and PDF and emailed at most once
  • An MCP server and a self-hosted OAuth 2.1 authorization server, so AI assistants work inside a workspace with the user's own permissions

How it fits together

API
One deployable that resolves the user's organization and workspace on the server and enforces the permission matrix on every route.
Single task write path
The only code that creates or changes tasks, so history, notifications, webhooks, re-indexing and real-time updates are never skipped.
AI gateway
Wraps every model call with feature flags, token budgets, data scrubbing, prompt versions and an audit record.
Background workers
Run assistant replies, triage, digests, standups, executive reports and batch AI jobs off a Redis-backed queue.
PostgreSQL with pgvector
Holds all workspace data and serves hybrid search from full-text and vector indexes, with no separate search cluster.
MCP server
A thin layer over the public API that forwards the user's own token and returns minimal, schema-exact results.

What happens when you ask ChatGPT to create a task

  1. ChatGPT discovers the app's authorization server and registers itself as a client, using the standard OAuth flow that connectors expect.
  2. The user signs in on the app's own consent page with their existing account and approves access.
  3. ChatGPT calls a tool on the MCP server, which forwards the user's token to the public API.
  4. The API validates the token, derives the workspace from the user's membership, and checks permissions exactly as it would for a request from the web app.
  5. The task is created through the single write path, so history, notifications, webhooks and search indexing all run.
  6. The MCP server returns a minimal result with no internal identifiers, and teammates see the new task appear on their boards in real time.

Decisions and trade-offs

One task write path

Why
Without it, import, triage, automations, the assistant and MCP would each forget a side effect, and the bugs would show up as missing history or silent webhooks.
Instead of
Side effects in route handlers or ORM event hooks.
The cost
A large module that everything depends on, and every new side effect has to be added there.

Facts first for AI summaries

Why
Rules compute the numbers, the model only writes the sentences, and a validator rejects any number or task reference that is not in the facts. A summary cannot claim twelve overdue tasks when there are three.
Instead of
Letting the model read raw data and write the summary.
The cost
More code per feature, and output that is sometimes plainer than free-form text.

The AI proposes drafts and a person approves them

Why
Drafts are checked against real projects and people, then applied through the normal write path. That builds trust, and every approval or rejection becomes an outcome signal for evaluation.
Instead of
Letting the AI write tasks directly.
The cost
One extra click per change.

Separate budgets for interactive and background AI

Why
An audit showed scheduled jobs consuming the shared budget, so users were refused because of work they never asked for.
Instead of
One global budget per workspace.
The cost
Three budgets to tune instead of one.

A self-hosted OAuth server for MCP

Why
Assistant connectors require a real OAuth flow, and building on the existing accounts means users connect with the login they already have.
Instead of
A managed identity provider, or pasting personal tokens, which connectors reject.
The cost
I own the security of that server, so MCP is read-only by default and abuse protection is a pre-launch requirement.

Hybrid search inside Postgres

Why
Full-text and vector search run in the main database with no extra cluster, and a pure-code fallback lets the tests run without the vector extension.
Instead of
Elasticsearch or a dedicated vector database.
The cost
A dedicated retrieval tier will be needed if vector search ever saturates.

The hard parts

  • Dependency cycles under concurrency

    Two people linking A to B and B to A at the same moment could create a loop. I serialised the cycle check per workspace with a transaction-scoped lock. I also treated 'done' as a status category rather than a fixed key, so custom workflows still unblock dependent tasks correctly.

  • Making AI trustworthy and affordable

    A self-audit found AI features with inconsistent behaviour in the UI, blocking calls inside async handlers, and background jobs eating user budgets. I centralised the gateway, added versioned prompts checked by tests, split the budgets, introduced facts-first validation and streaming, and gave the frontend one shared contract for every AI result.

  • Connecting to ChatGPT

    Pasting a personal token was rejected, because connectors expect OAuth. I built a narrow authorization server with discovery, consent and tokens bound to the MCP resource, on top of the existing account system. Every MCP tool is annotated with whether it reads, writes or destroys data.

  • Frontend weight with a rich editor

    The rich-text editor and drag-and-drop libraries are heavy. I lazy-load every page, split CSS per route, keep shared hooks out of the entry bundle, and enforce byte budgets in the build, so a regression fails before it ships.

What I'd do next

  • Run the backend tests, end-to-end tests and bundle budgets in CI on every merge request.
  • Add queue-depth and job-age metrics, and split background queues by priority.
  • Move WebSocket and streaming connections into a dedicated real-time gateway once connection counts justify it.
  • Add database-level row security as defence in depth behind the application checks, then finish the ChatGPT app submission.

What I took away

When many things write the same data, give them one door. The single task write path made everything after it cheap: AI drafts, automations and MCP all inherited correct behaviour without extra work. The same idea applies to AI itself. Put every model call behind one gateway, and let the model phrase facts instead of producing them.
